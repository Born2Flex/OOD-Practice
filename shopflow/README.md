## Phase 1: domain kickoff

### Pattern choices
One or two sentences per choice. Include the places where a pattern was **not** used.

| Area | Choice | Why | Rejected alternative |
|------|--------|-----|----------------------|
| Pricing and discounts | Strategy (`Discount`) + Composite (`StackedDiscount`) + Specification (`CustomerTypeSpecification`), coordinated by `PricingService` | **Keep `Order` cohesive (GRASP High Cohesion).** `Order` already has lines, a customer reference and a lifecycle; adding discount rules would push it toward a God Object (Large Class smell). **The calculation needs more than the order.** It also needs the `Customer`, which `Order` only references by ID. Evans recommends a *Domain Service* for an operation that isn't the natural responsibility of one entity; Larman calls this *Pure Fabrication*. **Not an anemic model.** The rules live in domain objects in `model.discount`, and `Order` still computes its own `subtotal()` (Information Expert). `PricingService` only coordinates. | **`Order.total(pricingPolicy)`** (Information Expert): rejected because it lowers `Order`'s cohesion and forces it to know about customers. **All logic in the service** (Transaction Script): rejected because it leads to the Anemic Domain Model that Fowler warns about. |
| Order lifecycle | State pattern | Avoids `if`/`else` or `switch` on the status inside `Order`: each state owns its allowed transitions, which keeps the behaviour maintainable. Invalid transitions throw a business exception (`IllegalOrderTransitionException`). | Enum-based transition table: one central enum that declares the allowed transitions for each status. Workable, but the State pattern is simple enough for now. |
| Notifications | Observer, hand-written in plain Java: `OrderEventPublisher` (subject), `OrderEventListener` (observer), `EmailNotifier`. One generic event, `OrderStatusChanged`, published by services | **Decouple the cause from the reactions (GRASP Low Coupling).** `PaymentService` only announces that the status changed and doesn't know who reacts. New channels such as SMS or an audit log subscribe without changing it (OCP). **Keep `Order` cohesive.** Services publish, so `Order` holds no listeners or event plumbing, consistent with the pricing decision. **One generic event.** `OrderStatusChanged(from, to)` covers every transition, and listeners decide what matters to them. **Protected Variations at the edges.** `EmailSender` hides how mail is sent, and `CustomerDirectory` hides where customers come from; tests use in-memory versions. **A notification must not undo a payment.** The publisher catches and logs listener failures, so a broken mail server can't fail a payment that was already charged. | **Spring events** (as the guide suggests): postponed until Phase 3, because Phase 1 is plain Java. **`PaymentService` calls `EmailNotifier` directly**: rejected because every new channel would change payment code. **`Order` as the GoF subject** (holds listeners): rejected because it adds observer management to `Order`. **Typed sealed events** (`OrderPaid(transactionId)`, ...): safer and can carry event-specific data, but more classes than needed today. **`Order` records events, the service pulls and publishes them** (DDD domain events): guarantees no transition is forgotten; deferred to Phase 4. **Known costs:** every service must remember to publish (only payment does today), and a failed email is logged but lost (Transactional Outbox in Phase 5). |
| Payment providers | Adapter (`StripeAdapter`, `PayPalAdapter`) behind our `PaymentGateway` interface + Factory (`PaymentGatewayFactory`, routes by currency), coordinated by `PaymentService` | **The provider APIs are incompatible.** Stripe takes `long` cents and throws a checked exception on decline; PayPal takes a `String` amount, needs two calls (create, then capture) and reports declines as a status. Each Adapter translates its SDK into one `charge(Money)` contract, so `PaymentService` never sees provider types (GRASP Indirection, Protected Variations), and an SDK change touches one class. **Provider choice is one routing rule** (USD → Stripe, EUR → PayPal). The Factory keeps it in a single place, and callers ask for "a gateway for this currency". **Declines are exceptions** (`PaymentDeclinedException`), consistent with invalid order transitions; a caller can't silently ignore them. **Tell-Don't-Ask on `Order`.** `canBePaid()` lets the State answer instead of the service checking the status, and `confirmPayment(TransactionId)` records what happened. The guard runs before the charge and the transition after approval, so a cancelled order is never charged and a declined one never becomes PAID. | **Provider calls inside `PaymentService`**: rejected because it couples the service to every SDK's types and quirks. **Registry `Map<Currency, PaymentGateway>`** instead of a `switch`: closer to OCP, but not worth it for two providers; revisit at the third. **Result object** (`Approved` / `Declined`) instead of an exception: more explicit for an expected outcome, but inconsistent with the rest of the model. **`order.payWith(gateway)`** (pure Tell): rejected because `Order` would coordinate payments, and its state would change before the charge. **Known costs:** `service` depends on the concrete factory in `integration` (classic N-Tier, not Hexagonal), and charging and `confirmPayment` are not atomic (sagas and idempotency in Phase 5). |

### Where I chose not to use a pattern
- **`PaymentGatewayFactory` uses a plain `switch` on the currency, not a registry.** With two providers, a `switch` is the simplest code that works and shows the whole routing rule in one place. A registry (`Map<Currency, PaymentGateway>` filled at construction) would let a new provider be added without editing the factory (OCP), but that flexibility isn't needed yet (YAGNI). **Revisit when** a third provider arrives or routing has to change without a code change.
